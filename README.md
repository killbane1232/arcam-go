# Arcam

Go-сервис исследования и исполнения криптовалютных стратегий. Один бинарный файл включает REST API, MCP, фоновые бэктесты, paper/live-сессии и веб-интерфейс без Node.js и внешнего CDN.

## Запуск

Требуется Go ≥ 1.26, Linux или macOS. Проверено с Go 1.27.3.

```sh
go run ./cmd/arcam
```

Откройте [http://127.0.0.1:8080](http://127.0.0.1:8080). Нажмите **Запустить бэктест**: уже выбраны `trend-demo v1`, BTCUSDT/ETHUSDT, 5 января — 1 февраля 2025 года. Источник **demo содержит синтетические свечи**, не котировки биржи. Загрузить реальные данные можно на вкладке «История рынка».

```sh
make build
./bin/arcam -addr 127.0.0.1:8080 -data ./data
make check
```

Начальные настройки читаются из переменных окружения. Подключения LLM также настраиваются в интерфейсе без перезапуска. `.env` автоматически читает только Compose:

```sh
cp .env.example .env
# Заполните .env; для Docker обязательно задайте ARCAM_API_TOKEN.
set -a
. ./.env
set +a
go run ./cmd/arcam
```

Docker Compose запускает готовый образ `ghcr.io/killbane1232/arcam-go:latest` после его первой публикации через GitHub Actions:

```sh
cp .env.example .env
# Задайте ARCAM_API_TOKEN в .env; сгенерировать токен: openssl rand -hex 32
docker compose pull
docker compose up -d
docker compose logs -f arcam
```

Сервис доступен на [http://127.0.0.1:8080](http://127.0.0.1:8080), данные сохраняются в именованном томе `arcam-data`. В `.env` можно изменить `ARCAM_IMAGE` (например, закрепить release-тег), `ARCAM_PORT` и `ARCAM_BIND_ADDRESS`. Для Ollama на хосте используется `OLLAMA_BASE_URL=http://host.docker.internal:11434`. В контейнере `127.0.0.1` обозначает сам контейнер.

Для доступа с других машин задайте адрес привязки и разрешите IP сервера или домен из адресной строки. Например, для `http://192.168.31.51:20000/`:

```dotenv
ARCAM_BIND_ADDRESS=0.0.0.0
ARCAM_PORT=20000
ARCAM_ALLOWED_HOSTS=192.168.31.51
```

`ARCAM_ALLOWED_HOSTS` принимает IP, домены и подсети CIDR (IPv4/IPv6). Например, `ARCAM_ALLOWED_HOSTS=192.168.31.0/24` разрешает IP сервера в диапазоне `192.168.31.0–192.168.31.255`. Можно смешивать записи через запятую: `192.168.31.0/24,arcam.example.com,fd00:31::/64`; пробелы вокруг записей игнорируются. Указывайте адреса без `http://`, порта и пути. Проверяется Host из URL запроса, а не IP клиента; домены не разрешаются через DNS для проверки подсети. Некорректный CIDR не разрешает доступ.

`0.0.0.0` в адресе привязки открывает порт на всех интерфейсах, но не разрешает все значения Host. Ошибка `Host not allowed` означает, что адрес запроса отсутствует в разрешённом списке. После изменения `.env` пересоздайте контейнер: `docker compose up -d --force-recreate arcam`; обычный `docker compose restart` не применяет новые переменные окружения. Поддержка CIDR требует образа, собранного из версии с этой возможностью.

Для обновления образа выполните `docker compose pull && docker compose up -d`. Для локальной сборки из исходников:

```sh
docker build -t arcam:local .
ARCAM_IMAGE=arcam:local docker compose up -d --pull never
```

`Dockerfile` собирает статический Go-бинарник и запускает его от UID/GID 10001, с CA-сертификатами, `/healthz` и постоянным томом `/data`. BuildKit поддерживает `linux/amd64` и `linux/arm64`; ключи и локальная история не попадают в build context/образ. Для bind mount каталог данных должен быть доступен UID 10001.

В [.github/workflows/image.yml](.github/workflows/image.yml) настроены `go vet`, `go test -race` и сборка обеих архитектур после успешных проверок. В pull request образ собирается без публикации; push в `main`/`master` или тега `v*` публикует в `ghcr.io/<owner>/<repo>` (для этого репозитория — `ghcr.io/killbane1232/arcam-go`). Ручной запуск доступен через **Actions → Docker image → Run workflow**: публикация разрешена только для `main`/`master` и тегов `v*`, остальные ветки только проверяются.

Образ получает тег ветки или релиза (например, `main` или `v1.2.3`), `sha-<полный SHA>` и `latest` для основной ветки. Слои сборки кэшируются в GitHub Actions; Actions закреплены на commit SHA. Для GHCR используется встроенный `GITHUB_TOKEN` с `packages: write`, дополнительные секреты не нужны; в репозитории должны быть разрешены Actions и публикация пакетов. Сам файл workflow не создаёт GitHub-репозиторий и не отправляет код.

После первой успешной публикации образ можно скачать командой:

```sh
docker pull ghcr.io/killbane1232/arcam-go:latest
```

## Возможности

- Визуальный конструктор и JSON DSL: EMA, SMA, RSI, ATR, Aroon, Ichimoku, MACD, Bollinger Bands; вложенные `all`, `any`, `not`.
- Независимые `enter_long`, `exit_long`, `enter_short`, `exit_short`. Сравнения с числами/индикаторами и пересечения.
- Условия позиции `none`/`long`/`short`, ссылки на сигналы входа в правилах выхода, пример закрытия по встречному сигналу.
- Неизменяемые версии стратегий с SHA-256. Редактирование создаёт новую версию. Запуск всегда фиксирует конкретную версию.
- OpenAI-совместимые Chat Completions и нативный Ollama: численные оценки действий, объяснение, строгая проверка ответа, постоянный кэш, лимит вызовов.
- Бэктест нескольких пар на заданном интервале; снимок входных свечей, хэши, решения, дерево условий, сделки и кривая капитала сохраняются на диск.
- Прогресс бэктеста по свечам всех пар и среднее время ответа LLM за запуск; попадания в кэш учитываются отдельно, замеры доступны во время расчёта и в итоговом отчёте.
- Промежуточные графики, решения, сделки и открытая позиция появляются во время расчёта. Передаются только новые строки; ручной просмотр истории сохраняется. Отмена/ошибка сохраняет уже рассчитанную часть отчёта.
- Кнопка «Продолжить» для failed-запуска: тот же ID, конфигурация и снимок данных, восстановление позиции и прогресса без повторных решений на готовых свечах. Лимит LLM общий для всех попыток.
- Свечной график, маркеры исполнений, точки всех решений, просмотр индикаторов, переход по истории, журнал причин и экспорт JSON.
- Публичная история Binance Spot / USD-M Futures, CSV из других источников и экспорт CSV. Свечи хранятся в SQLite: отдельный файл на пару, разделение по источнику и таймфрейму внутри базы.
- Paper-сессии на текущем рынке и реальные Binance USDT perpetual market-ордера. Адаптеры данных и исполнения отделены от движка.
- Исследовательский MCP через Streamable HTTP и stdio на официальном Go SDK v1.8.0.

## Стратегии

Примеры: [EMA + Aroon](examples/ema-aroon.json), [Ichimoku](examples/ichimoku.json), [EMA + LLM](examples/ema-llm.json). Файл содержит тело `Strategy`; для сохранения REST принимает `{ "id": "my-strategy", "strategy": ... }`.

```json
{
  "all": [
    {"left":{"field":"fast.value"},"op":"gt","right":{"field":"slow.value"}},
    {"left":{"field":"llm.enter_long"},"op":"gte","right":{"value":0.75}}
  ]
}
```

| Индикатор | Параметры | Выходы `id.<поле>` |
|---|---|---|
| ema, sma | period | value |
| rsi, atr | period | value |
| aroon | period | up, down, oscillator |
| ichimoku | fast=9, slow=26, period=52, displacement=26 | tenkan, kijun, span_a, span_b |
| macd | fast=12, slow=26, signal=9 | line, signal, histogram |
| bollinger | period=20, multiplier=2 | middle, upper, lower |

Базовые поля: `open`, `high`, `low`, `close`, `volume`. Операторы: `gt`, `gte`, `lt`, `lte`, `eq`, `crosses_above`, `crosses_below`. Для отключения стороны удалите её вход/выход. Числа задаются в `{"value": 70}`, ссылки — в `{"field":"trend.up"}`.

Валидация проверяет параметры, ссылки, наличие выхода, уникальность ID, максимальную глубину 16 и 256 узлов правил. Непрогретый операнд делает проверяемое условие неготовым: `not` не превращает его в сигнал. Группы вычисляются с коротким замыканием: `all` прекращает проверку при первом ложном/неготовом условии, `any` — при первом истинном. Пропущенные ветки не влияют на результат. При одновременном long/short сигнале движок выбирает hold. В одной паре может быть только одна позиция; разворот требует сначала закрытия.

Условие `{"position":"none"}` разрешает вход только вне позиции. Для выхода из long при сигнале входа short:

```json
{"all":[{"position":"long"},{"signal":"enter_short"}]}
```

В конструкторе это типы **Состояние позиции** и **Сигнал входа**. `signal` разрешён только в правилах выхода и ссылается на включённое `enter_long`/`enter_short`. Ссылка проверяет вход как для `position=none`, поэтому явный запрет входа при открытой позиции не блокирует выход по встречному сигналу. Индикаторы и оценки LLM используются от текущей свечи; дополнительного вызова модели нет. Сначала выполняется только выход; новый вход требует следующего решения. Защита от второй позиции действует и без явного условия. В журнале сохраняются фактическая позиция и дерево проверки ссылки. Пример: [examples/position-trend.json](examples/position-trend.json), кнопка «Позиция и встречный сигнал».

## Семантика бэктеста

1. Все даты — RFC3339 UTC. `from` включительно, `to` исключительно, обе даты на границе таймфрейма. Включаются только полностью закрытые свечи.
2. Для `binance_futures` / `binance_spot` пропуски, включая `warmup` свечей **до** `from`, дозагружаются автоматически. `POST /api/strategies/validate` возвращает необходимый запас. Для DEMO/CSV требуется полное локальное покрытие; свечи не дорисовываются и источники не подменяются.
3. Сигнал вычисляется после закрытия свечи. Исполнение — на открытии следующей. Сигнал последней свечи сохраняется, но не исполняется; открытая позиция закрывается по последнему close с расходами.
4. EMA начинает с SMA периода; RSI/ATR используют сглаживание Wilder. Aroon смотрит на `period+1` свечей, при равных экстремумах берёт последний. Bollinger использует population standard deviation. Ichimoku spans берутся из прошлого с displacement; будущая Chikou-линия в сигналы не включена.
5. Капитал поровну распределяется между парами. `position_fraction` применяется к текущему капиталу пары. Это независимые счета, без общего маржинального обеспечения и кредитного плеча. Short — модель PnL, а не реальная возможность шортить спот.
6. `fee_bps` и `slippage_bps` задаются на каждую сторону сделки, 1 bps = 0.01%. С учётом комиссии размер позиции не превышает выделенный капитал. Учитываются вход и выход, включая принудительный выход в конце.
7. Stop loss / take profit в бэктесте проверяются по OHLC. При двух касаниях в одной свече приоритет у стопа. Гэп через стоп исполняется по худшей цене открытия. Время внутрисвечного исполнения помечается концом свечи: точного времени из OHLC узнать нельзя.
8. Не моделируются funding, заём, ликвидации, стакан, частичные исполнения и задержки. Проскальзывание — фиксированные bps. Для LLM возможна утечка исторических знаний из обучения модели; causal-входы сами по себе её не исключают.

Ограничения: 10 пар, 50 000 тестовых свечей на пару, 32 индикатора, 2 параллельных прогона, до 8 активных/ожидающих заданий, 250 000 свечей в локальном наборе. Для бэктеста из SQLite читается только выбранный диапазон с прогревом; полный экспорт читает весь набор. Это однопроцессная реализация для локальной лаборатории.

Дозагрузка выполняется в фоне в статусе `preparing`, занимает слот задания и отменяется через обычный `cancel`. Проверяются все отсутствующие интервалы: начало, внутренние разрывы и конец. Загружаются только отсутствующие свечи пакетами до 5000, с сохранением в SQLite. Параллельные подготовки одного набора повторно используют уже загруженное. Доступные при создании задания свечи фиксируются сразу; остальные добавляются в снимок до начала расчёта. Последующие импорты не меняют этот снимок. В отчёте `data_loads` перечислены реально загруженные диапазоны, а `progress` показывает текущую загрузку. Если биржа не отдаёт часть периода, задание завершается с точными границами пропуска; корректно полученная часть остаётся в БД.

Ошибка покрытия всегда относится к выбранному **source + symbol + interval**. Наличие BTCUSDT в файле SQLite не означает наличие нужных дат в источнике DEMO. При нехватке DEMO/CSV сообщение указывает источник, первый пропуск, различает прогрев и тестовый период и подсказывает другие наборы с подходящими датами.

## LLM

Откройте **Настройки**: отдельные подключения OpenAI-compatible и Ollama содержат базовый URL, необязательный API-ключ, модель по умолчанию и таймаут 1–300 секунд. Для OpenAI доступен JSON mode. **Проверить** получает список моделей (`GET /models` или `/api/tags`), не запускает генерацию и не скачивает модели; проверяется текущий черновик без сохранения. После проверки список доступен в поле модели. **Сохранить** применяет параметры без перезапуска.

Пустое поле ключа сохраняет текущий ключ; отдельный флажок удаляет его. При смене адреса с настроенным ключом нужно ввести ключ заново или удалить его. API возвращает только `api_key_configured`. Сохранённые подключения лежат в `data/settings/llm-{provider}.json` с правами 0600 и имеют приоритет над окружением. Ключи не шифруются на диске; доступ к каталогу данных должен быть только у владельца сервиса.

В конструкторе кнопка «Подставить модель из настроек» копирует модель в стратегию. Версия стратегии сохраняет конкретное имя модели. Подключение фиксируется при начале исполнения прогона / активации сессии; изменение настроек не меняет текущий прогон. Начальные значения из окружения:

- `provider: "openai"`: `OPENAI_BASE_URL` (с `/v1`), `OPENAI_API_KEY`, `OPENAI_MODEL`. По умолчанию `response_format=json_schema`; для совместимых серверов без Structured Outputs задайте `LLM_JSON_MODE=true`.
- `provider: "ollama"`: `OLLAMA_BASE_URL`, необязательные `OLLAMA_API_KEY`, `OLLAMA_MODEL`; `/api/chat`, `stream=false`, JSON Schema в `format`.

Модель получает последние `lookback` закрытых свечей, текущие рассчитанные индикаторы, пару, сторону позиции и инструкцию стратегии. Возвращает:

```json
{"enter_long":0.8,"exit_long":0.1,"enter_short":0.2,"exit_short":0.7,"reason":"Объяснение на основе переданных признаков"}
```

Эти числа используются как `llm.enter_long` и т. д. Порог и комбинацию с обычными индикаторами определяют правила. Это оценки модели, не гарантированно калиброванные вероятности. Ошибки API, отказ модели, незавершённый ответ, неверный JSON или исчерпание лимита останавливают прогон/ставят сессию на паузу; модель не заменяется скрытой эвристикой.

LLM вызывается по необходимости. Сначала проверяются условия индикаторов/позиции и дешёвые вложенные ветки; порядок в сохранённой стратегии менять не нужно. `all` отбрасывается сразу после неуспешной проверки, затем вычисление продолжается выше по дереву. `any` с уже истинной веткой не требует модели. Неопределённое условие LLM не считается ложным: необходимость ответа передаётся вверх через `all`/`any`/`not` и может исчезнуть, если другая ветка определила результат. Вне позиции проверяются только входы (включая возможный конфликт long/short), в позиции — соответствующий выход; ссылки на входы раскрываются по мере необходимости.

Если результат ещё зависит от LLM, выполняется один запрос/обращение к кэшу на свечу и пару, четыре оценки применяются вместе, затем активные правила проверяются заново. Неиспользуемый LLM-индикатор не вызывает провайдера. В журнале есть `llm_status` и признаки пропущенных условий; счётчик «пропущено» показывает число свечей, где модель не требовалась. Ошибка необходимого запроса по-прежнему останавливает расчёт.

Для `crosses_above`/`crosses_below` по полям `llm.*` нужны оценки на **двух соседних свечах**. Пропущенные ответы не переносятся вперёд и не достраиваются. Если предыдущая свеча обошлась без LLM, первый достигнутый вызов создаёт только текущее значение; пересечение ещё не готово. Обычные пересечения индикаторов не меняются.

Для вызовов нужны `allow_llm=true` и `max_llm_calls>0`. Бюджет общий для всех пар одного прогона; для сессии — на каждый явный запуск/возобновление. Кэш и пропуски не расходуют бюджет. SHA-256 включает endpoint, модель, инструкцию, схему, свечи, индикаторы и позицию. В отчёте остаются ответ, имя модели, request hash и отметка кэша. Для воспроизводимости используйте фиксированный ID модели; алиас может меняться, а кэш удерживает первый ответ для одинакового запроса.

## LiquidAI/d1-2B: временный пресет

В библиотеке доступна стратегия `trend-d1-2b v1` (при включённом демозаполнении): EMA + Aroon + четыре оценки d1. Входы требуют подтверждения модели ≥ 0.75, выходы — разворота EMA или оценки выхода ≥ 0.75. Пример: [examples/ema-d1-2b.json](examples/ema-d1-2b.json). Пресет создаётся отдельно; существующие версии не изменяются. Кнопка **LiquidAI/d1-2B · Ollama** выбирает модель в текущем черновике, а **+ EMA / LiquidAI d1-2B** создаёт черновик со всеми правилами.

d1 — модель решений: используется `protocol: "systemone"`, запрос `{model,state,questions}` с четырьмя вопросами `type: "noul"`; ответы `answers.<action>.noul` напрямую становятся `llm.enter_long`, `llm.exit_long`, `llm.enter_short`, `llm.exit_short`. Текстового объяснения модель не генерирует: журнал явно показывает сводку численных оценок и дерево правил. Это не обещание прибыльности и не калиброванная вероятность результата сделки.

Установите Ollama с поддержкой d1-2B и System One (сам endpoint требует ≥ 0.35.0), запустите сервер и загрузите **точный тег 2b**:

```sh
ollama serve
# В другом терминале:
ollama pull d1:2b
```

В «Настройках» укажите URL Ollama (обычно `http://127.0.0.1:11434`), при желании модель по умолчанию `d1:2b`, нажмите «Проверить». Для бэктеста разрешите LLM и задайте бюджет вызовов. Пресет обращается к `/v1/systemone`; неподдерживаемый endpoint или отсутствующая модель возвращают ошибку без замены другим провайдером. Установка Ollama и весов модели не входит в запуск Go-сервиса.

Для другого System One сервера можно выбрать `provider: "openai"`, `protocol: "systemone"`, указать его базовый URL с `/v1` и имя модели, опубликованное сервером (например `LiquidAI/d1-2B`). Это использует `/systemone`, а не `/chat/completions`. Обычные chat-модели продолжают работать с отсутствующим `protocol` или `protocol: "chat"`.

## Paper и live

Создайте сессию во вкладке «Торговые сессии». Версия и режим фиксируются при создании. Переключение paper → live означает создание **новой** live-сессии; бумажные позиции на биржу не переносятся.

Paper использует текущую публичную цену Binance и моделирует комиссии/slippage. Новая закрытая свеча оценивается один раз; сигнал старше 30 секунд не исполняется. За время вызова LLM свежесть проверяется повторно. Risk-проверки выполняются каждые 5 секунд по текущей цене, в отличие от исторической OHLC-модели.

Для live:

```sh
export ARCAM_API_TOKEN='your-long-random-token'
export BINANCE_API_KEY='your-key'
export BINANCE_API_SECRET='your-secret'
export ENABLE_LIVE_TRADING=true
export MAX_LIVE_ORDER_NOTIONAL=100
go run ./cmd/arcam -data ./live-data -seed-demo=false
```

В интерфейсе укажите API-токен, точную версию, пары и `mode=live`. Поддержаны только Binance USD-M **USDT perpetuals, one-way mode**. Изначальные позиции должны быть нулевыми; внешние открытые ордера запрещены. Плечо и margin mode сервис не меняет. Номинал каждого входа ограничен серверным лимитом и лимитом сессии. Одна live-сессия резервирует свои пары, включая паузу с открытыми позициями.

Перед отправкой ордера: сверка позиции и открытых ордеров, exchange lot/min-notional filters, округление количества вниз десятичной арифметикой, атомарная запись намерения. Выход — `reduceOnly`. Подпись HMAC-SHA256, время берётся у биржи. Рыночный POST автоматически не повторяется. При таймауте, частичном исполнении или неизвестном статусе сессия остаётся с `pending` и требует `reconcile`, который делает GET по clientOrderId. Только полное подтверждённое исполнение обновляет внутреннюю позицию.

Команды: `pause` останавливает обработку, **сохраняя позицию**; `close` закрывает учтённые позиции market-ордерами и останавливает сессию; `reconcile` сверяет pending-ордер, оставаясь на паузе; `resume` явно продолжает после сверки. После перезапуска сессии автоматически не возобновляются. Если pending-ордер отклонён/отменён или биржа не находит его, автоматическое восстановление блокируется: сначала нужна ручная сверка на бирже. Нельзя считать отсутствие ответа доказательством отсутствия исполнения.

**Текущие границы live:** stop loss / take profit работают в процессе, а не как биржевые защитные ордера; при выключенном/зависшем сервисе или паузе защиты нет. Учёт комиссий и баланса live оценочный по `fee_bps`, не выписка аккаунта; funding/ликвидации и внешние изменения позиции не восстанавливаются автоматически. Частичные/отменённые ордера требуют ручного разбора. Реальный аккаунт в разработке не использовался; перед эксплуатацией нужен прогон на вашей тестовой среде биржи и отдельная проверка исполнения. `BINANCE_FUTURES_BASE_URL` меняет и feed, и execution; используйте отдельный каталог данных для каждой среды.

## REST и MCP

Подробные запросы: [docs/api.md](docs/api.md), готовые тела в [examples](examples).

HTTP MCP: `http://127.0.0.1:8080/mcp`. Если задан токен — `Authorization: Bearer …`. Клиент должен поддерживать Streamable HTTP. SDK согласует версию протокола; transport stateless, без отдельных SSE/session endpoints.

```json
{"mcpServers":{"arcam":{"url":"http://127.0.0.1:8080/mcp"}}}
```

Конкретное имя поля (`url`/`httpUrl`) зависит от клиента. Для stdio:

```json
{"mcpServers":{"arcam":{"command":"/absolute/path/arcam/bin/arcam","args":["-mcp-stdio","-data","/absolute/path/arcam/mcp-data"]}}}
```

Stdout занят протоколом, логи идут в stderr. Не запускайте HTTP и stdio с одним каталогом: межпроцессный flock блокирует второго писателя. Для одной общей лаборатории подключайте клиентов к HTTP.

Инструменты: `get_catalog`, `list_strategies`, `validate_strategy`, `save_strategy`, `list_datasets`, `import_history`, `run_backtest`, `resume_backtest`, `list_backtests`, `get_backtest`, `get_decisions`, `compare_backtests`, `cancel_backtest`. Создание версий требует JSON в `strategy_json`. `get_backtest` возвращает компактные метрики; `get_decisions` — до 200 свечей/решений за запрос. `resume_backtest` принимает ID упавшего запуска и продолжает его с сохранённой точки; REST/UI используют тот же механизм. Сравнение отмечает совпадение входных данных и расходов. Проверочные периоды выбираются явно отдельными прогонами; автоматического оптимизатора/walk-forward здесь нет.

Готовый [скилл Arcam Research](skills/arcam-research/SKILL.md) работает с Codex и Hermes Agent: воспроизводимые эксперименты, DSL, прогрев, сравнение результатов и диагностика MCP. [Установка и примеры запросов](docs/agent-skills.md). Read-only проверка: `python3 skills/arcam-research/scripts/mcp_smoke.py`.

## Хранение и расширение

Свечи физически разделены по парам: `data/candles/BTCUSDT.sqlite`, `ETHUSDT.sqlite` и т. д. Новые файлы создаются автоматически при импорте. Внутри каждой базы первичный ключ `(source, timeframe, open_time)` разделяет рынки/таймфреймы и ускоряет выборку по датам. Повторный импорт обновляет совпадающие свечи. SQLite работает в WAL, запись одного импорта транзакционна; отдельные пары могут записываться параллельно. Используется pure Go драйвер `modernc.org/sqlite`, CGO и отдельный сервер БД не нужны. Закрытые свечи paper/live-сессий также сохраняются.

При первом запуске старые `data/datasets/*.json` автоматически переносятся в соответствующие SQLite-файлы. Исходники остаются как `*.json.migrated`. Миграция отмечается в самой базе в одной транзакции с данными; повторный запуск не перезаписывает обновлённые свечи старой резервной копией. При ошибке миграции запуск прерывается с указанием файла. Вкладка «История рынка» и `GET /api/storage` показывают базы и число свечей. Для резервной копии остановите процесс и копируйте весь каталог `data`; нельзя копировать только `.sqlite` при активной записи в WAL.

`data/strategies`, `runs`, `llm`, `sessions`, `settings` — JSON с atomic rename, fsync, правами 0600 и блокировкой каталога. В `Run.input_data` сохраняются исходные свечи **с прогревом**. Большие результаты получают только по отдельному ID, списки возвращают метаданные. Журнал активной сессии ограничен последними 5000 событиями; результаты бэктестов сохраняются целиком.

Внешний bind требует API-токен; live тоже требует токен. Для доступа по IP сервера или домену добавьте этот IP, домен или CIDR-подсеть в `ARCAM_ALLOWED_HOSTS`, без схемы и порта. Подсеть проверяется по Host запроса; это не фильтр IP клиентов. Origin/Host проверяются, тело запроса ограничено, ключи биржи и LLM не возвращаются в UI. Токен UI хранится в sessionStorage вкладки. Данные и доступ к LLM общие для одного владельца сервиса: здесь нет пользовательских ролей или multi-tenant изоляции.

Новая биржа реализует `market.DataSource` (история/пары) и `execution.Broker` (цена, позиция, проверка аккаунта, нормализация, отправка и поиск ордера). Зарегистрируйте реализации в `Service.Sources` / `Sessions.Brokers` и каталоге UI. Реализован Binance; Bybit, OKX и другие адаптеры пока не реализованы. Ядро стратегии от API биржи не зависит.
