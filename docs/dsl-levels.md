# DSL: контексты, уровни и план входа

Расширения доступны в историческом бэктесте и paper/live-сессиях через JSON, REST и MCP. Полный пример: [levels-retest.json](../examples/levels-retest.json). Это демонстрация синтаксиса, а не проверенная торговая гипотеза. Исходные стратегии с `field`/`value` и процентными `stop_loss`/`take_profit` сохраняют прежний смысл.

## Закрытые старшие свечи

```json
[
  {"id":"daily","type":"ohlc","timeframe":"1d"},
  {"id":"adr5","type":"adr","period":5,"timeframe":"1d"},
  {"id":"atr14","type":"atr","period":14,"timeframe":"1d"},
  {"id":"trend","type":"ema","period":20,"timeframe":"4h"},
  {"id":"pivot","type":"pivot","left":2,"right":2,"timeframe":"4h"}
]
```

У любого индикатора есть необязательный `timeframe`. Он должен быть не меньше торгового интервала и делиться на него без остатка. Без поля используется торговый интервал. Контексты агрегируются из тех же замороженных младших свечей в `Run.input_data`; исходные данные всех контекстов покрыты `PairResult.data_hash`. Отдельный биржевой источник старших свечей не используется.

Агрегат доступен только после закрытия всех входящих свечей. Неполные начальные/конечные бакеты и бакеты с пропусками отбрасываются. Пропуск старшего бара сбрасывает индикаторный прогрев. Значение закрытого старшего бара переносится на последующие младшие бары до следующего закрытия. `<id>.bar_time` — время открытия контекстного бара, `<id>.available_at` — время его закрытия, оба в Unix seconds UTC.

Новые типы:

| Тип | Параметры | Выходы |
|---|---|---|
| `ohlc` | без периода | `open`, `high`, `low`, `close`, `range`, `volume` |
| `adr` | `period` 2..1000 | `value`: среднее High−Low последних закрытых баров; для ADR нужен `timeframe: "1d"` |
| `pivot` | `left`, `right` 1..1000 | `high`, `low`, `high_time`, `low_time`, `high_confirmation_bar`, `low_confirmation_bar` |

Pivot — строгий экстремум относительно `left` предыдущих и `right` следующих баров; равные экстремумы не подтверждаются. Он становится доступен на закрытии последнего правого бара. `*_time` идентифицирует исходный экстремум, `*_confirmation_bar` — открытие подтвердившего бара. Уровень сохраняется до следующего подтверждения; до первого подтверждения поле отсутствует.

Доступны встроенные поля:

- `day.open/high/low/range/time/available_at` — текущий UTC-день торговой свечи, только известные бары. На первой свече нового дня диапазон сбрасывается. Если начало дня отсутствует в истории, диапазон недоступен.
- `previous_day.open/high/low/close/range/time/available_at` — предыдущий полный UTC-день относительно даты открытия торговой свечи. `time` пригоден как идентификатор дневного уровня.

На свече 23:00–00:00 `day.*` ещё описывает заканчивающийся день; после её закрытия дневные индикаторы уже могут использовать этот полностью завершённый день. Внутри незакрытого дня ADR его не включает.

Автозагрузка учитывает старший прогрев, смещения и запас для выравнивания UTC-бакетов. Валидация возвращает `warmup_by_interval`: число младших свечей для каждого совместимого торгового интервала. Старое поле `warmup` остаётся оценкой в барах индикатора. Максимальный запас — 200 000 младших свечей.

## Смещения и арифметика

```json
{"field":"high","offset":1}
```

`offset` — 0..10000 торговых баров назад, только для `field`. У старшего поля это также смещение по торговым барам. Например, `daily.high` с `offset: 1` — значение, известное на предыдущем младшем баре; для вчерашнего High обычно удобнее `previous_day.high`.

```json
{"op":"div","args":[
  {"op":"sub","args":[{"field":"high"},{"field":"low","offset":1}]},
  {"field":"adr5.value"}
]}
```

`add/sub/mul/div/min/max` принимают ровно два операнда, `abs` — один. Выражения можно вкладывать; глубина ограничена 16. Неизвестное поле, недостаток истории, деление на ноль и переполнение делают условие неготовым, в том числе под `not`. Пересечения вычисляют всё выражение для текущего и предыдущего баров. Пропущенные исторические оценки LLM не достраиваются и не переносятся вперёд.

## Ожидание ретеста

```json
{
  "id":"breakout",
  "when":{"left":{"field":"close"},"op":"crosses_above","right":{"field":"previous_day.high"}},
  "key":{"field":"previous_day.time"},
  "capture":{"level":{"field":"previous_day.high"},"stop":{"field":"low"}},
  "expires_after":4,
  "cancel":{"left":{"field":"close"},"op":"lt","right":{"field":"setup.breakout.stop"}}
}
```

Это элемент массива `Strategy.setups` (до 16). `when` создаёт ожидание, `capture` атомарно сохраняет 1..16 конечных значений. Поля `setup.<id>.<name>` остаются привязаны к исходному событию. Также доступны `active`, `age`, `reference_time`, `expires_at`. В правиле входа используйте `{"setup":"breakout"}` вместе с условиями подтверждения.

Без `key` новое событие возникает при переходе `when` из false в true. С `key` событие возникает при true и строго возрастающем числовом ключе; используйте timestamp дневного уровня или pivot. Равные и более старые ключи повторно не используются даже после отмены/истечения. Пока ожидание активно, новые события его не заменяют. Во время открытой позиции новые ожидания не создаются. Во время прогрева события не создаются.

`age=0` на закрытии исходной свечи. Для ретеста только на следующей свече добавьте `age >= 1`. `expires_after=4` разрешает проверку на возрастах 0..4; возраст 5 уже просрочен. Отмена и истечение проверяются до правил входа. `when`, `key`, `capture` используют рыночные поля, без LLM или других setups; `cancel` дополнительно может читать собственные сохранённые значения.

Состояния и reference/expiry записываются в `Decision.setups` и контрольную точку пары. При постановке входа в очередь участвующие истинные `setup`-условия помечаются `consumed`: событию даётся одна попытка входа. Даже пропуск следующего open из-за гэпа не разрешает повторное использование. Если стратегия не содержит `setup`-условия в соответствующей ветке входа, сохранённое событие этим входом не потребляется.

## Защитные цены и денежный риск

```json
{
  "position_fraction":1,
  "stop_loss":0,
  "take_profit":0,
  "risk_fraction":0.005,
  "max_notional":10000,
  "max_stop_fraction":0.1,
  "max_entries_per_day":2,
  "long":{
    "stop_price":{"field":"setup.breakout.stop"},
    "target_price":{"op":"add","args":[{"field":"setup.breakout.level"},{"field":"atr14.value"}]}
  }
}
```

Для short предусмотрен симметричный `risk.short`. `stop_price` обязателен в заданной стороне, `target_price` необязателен. Абсолютные уровни вычисляются на сигнальном закрытии и сохраняются в плане; после входа они не пересчитываются. Недоступный, неположительный или расположенный с неправильной стороны уровень блокирует вход. Абсолютный стоп нельзя смешивать с `stop_loss`; абсолютную цель — с `take_profit`. Общая процентная цель допустима вместе с абсолютным стопом.

`risk_fraction` — доля текущего капитала пары, которую планируется потерять при штатном стопе. Количество считается на фактическом следующем open после проскальзывания. Риск на единицу включает расстояние до стопа, модель проскальзывания выхода и комиссии входа/выхода. `position_fraction` ограничивает капитал вместе с входной комиссией; `max_notional` дополнительно ограничивает номинал. Если рассчитанное по риску количество превышает предел, вход пропускается с причиной `notional limit`. Без `risk_fraction` сохраняется sizing по доле капитала, с ограничением `max_notional` при его наличии.

Дополнительные причины пропуска: гэп за стоп/цель, расстояние до стопа больше `max_stop_fraction`, недоступные данные, исчерпанный капитал. `max_entries_per_day` считает успешные входы отдельно по каждой паре, по UTC-дате исполнения. На следующем UTC-дне счётчик сбрасывается; отменённые заявки его не увеличивают. Нулевые значения необязательных лимитов отключают их.

При одновременном касании стопа и цели приоритет у стопа. Гэп уже открытой позиции может дать убыток больше планового R. Условия лимитного или внутрисвечного исполнения здесь не моделируются.

## Аудит, продолжение и редактор

`Decision.features` содержит использованные ATR/ADR и уровни, `Decision.plan` — сохранённый план следующего входа. `Decision.execution` на следующем баре содержит результат попытки, причину пропуска либо фактические entry/stop/target, количество, номинал и плановый риск. `entry_day`/`entries_today` объясняют дневной лимит.

План, setups, открытая позиция с защитными ценами и дневной счётчик входят в сохраняемый префикс `PairResult`. Продолжение failed-бэктеста восстанавливает их, включая историю полей для offset, не переоценивая готовые решения. `Trade.initial_risk`, `pnl_r`, `fees`, `stop_price`, `target_price`, `event_id` позволяют проверить net PnL в R и расходы.

Каталог MCP/REST возвращает раздел `dsl` с синтаксисом и готовым примером. JSON-редактор сохраняет новые поля риска; сложные условия отображаются в конструкторе как JSON без преобразования в простое сравнение.

Paper/live используют общие с бэктестом переходы setups, планирование защиты, расчёт количества и дневные лимиты. Сигналы вычисляются по закрытым свечам; отправка ордера разрешена только в первые 5 секунд после границы UTC. Прогрев не создаёт setups. При возобновлении пропущенные бары проверяют отмену и истечение ожидающего события; новые события, обнаруженные на пропущенных барах, не разрешают ретроспективный вход. Исторические LLM-оценки не достраиваются. Состояние setups и история runtime-полей для offset сохраняются.

План фиксирует технические stop/target на сигнальной свече, а количество рассчитывается по актуальной котировке. В live после округления брокером риск и лимиты проверяются ещё раз по свежей котировке. `slippage_bps` служит резервом при расчёте количества и риска стопа; фактическая цена берётся из подтверждённого исполнения без дополнительного slippage. Комиссии оцениваются по `fee_bps`. Лимиты номинала стратегии, сессии и сервера действуют одновременно. Использованное событие не переиспользуется при пропуске из-за гэпа, лимита или пропущенного окна отправки; дневная квота расходуется только исполненным входом.

Перед live-отправкой `Session.pending` сохраняет план, исходный баланс и время сигнала. При неизвестном результате отправка не повторяется: `reconcile` запрашивает ордер по client ID. Подтверждённый вход получает фактические цену/количество, фиксированные уровни и `initial_risk`; дата дневного счётчика берётся из времени исполнения UTC (при отсутствии времени в ответе — из времени отправки). Нарушившее риск исполнение сохраняется с `risk_breached`, после чего движок пытается закрыть позицию `reduceOnly`. При ошибке сохраняются позиция, нарушение и возможный pending для последующей сверки.

`Session.setups`, `daily_entries`, `positions`, `previous`, `input_data` и `pending` восстанавливаются из хранилища. `SessionEvent.execution` содержит аудит исполнения или пропуска, `SessionEvent.trade` — net PnL, расходы и результат в R. Защитные выходы проверяются по текущей цене каждые 5 секунд, включая середину свечи. Это локальная защита работающего процесса: биржевые stop-ордера не выставляются, при паузе/остановке сервиса защита не исполняется. Цена live-исполнения и внутрисвечные выходы могут отличаться от исторической OHLC-модели.

## Обязательные проверки причинности и исполнения

Проверки входят в обычный `make check` и CI (`go test -race ./...`), без доступа к реальной бирже:

- `internal/core/timeframe_contract_test.go`: изменение и добавление будущих OHLC не меняет прошлые признаки, решения, планы и исполнения; проверяются границы H4/D1 на 15m/1h и исключительный конец бэктеста.
- `internal/app/session_frames_test.go`: paper/live получают только закрытый диапазон, H4/D1 недоступны до закрытия; сессия и бэктест совпадают на 112 последовательных фреймах, включая long/short и восстановление из JSON.
- Там же проверяются отсутствие входа на 30-й секунде, однократная обработка границы, задержки данных/LLM/брокера/записи intent, неизменность момента доступной информации при переходе границы во время I/O и работа защитных выходов внутри свечи.
- `internal/market/binance_test.go`: адаптер не запрашивает незакрытый интервал и отклоняет формирующийся бар в ответе биржи.

Часы, рынок и брокер в тестах управляемые; wall-clock ожидания и отправка реальных ордеров не требуются. В live допускается только транспортное окно до 5 секунд после границы, с повторной проверкой непосредственно перед отправкой. Равенство решений проверяется при одинаковом исходном ряде; фактическая цена биржевого исполнения может отличаться.
