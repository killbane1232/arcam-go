# HTTP API

Base URL: `http://127.0.0.1:8080`. JSON-запросы: `Content-Type: application/json`. Если задан `ARCAM_API_TOKEN`, все `/api/*` и `/mcp` требуют `Authorization: Bearer <token>`. Ошибки: `{"error":"message"}`; неизвестные JSON-поля отклоняются. Время — UTC RFC3339.

|---|---|
| GET /healthz | `{"status":"ok"}` |

| GET /api/settings/llm | Подключения openai/ollama без ключей, с api_key_configured и source |

## Подключения LLM

`POST /api/settings/llm/openai` (все поля необязательны; неизвестные отклоняются):

```json
{"base_url":"https://api.openai.com/v1","api_key":"your-key","default_model":"your-model","timeout_seconds":60,"json_mode":false}
```

Для Ollama: `POST /api/settings/llm/ollama` с `base_url=http://127.0.0.1:11434`; `json_mode=true` не поддерживается. Пустой или отсутствующий `api_key` сохраняет ключ, `clear_api_key=true` удаляет его. Смена адреса требует нового ключа или очистки старого. Ключ никогда не возвращается, вместо него — `api_key_configured`.

`POST .../check` принимает тот же черновик или `{}` для текущего подключения. Только GET списка моделей, без генерации; изменения не сохраняются. Сохранённые настройки имеют приоритет над переменными окружения. Модель по умолчанию служит для конструктора; `Strategy.llm.model` по-прежнему обязателен и явно версионируется.

## Бэктест

```json
{"strategy_id":"trend-demo","version":1,"source":"demo","symbols":["BTCUSDT","ETHUSDT"],"interval":"1h","from":"2025-01-05T00:00:00Z","to":"2025-02-01T00:00:00Z","capital":10000,"fee_bps":4,"slippage_bps":2,"allow_llm":false,"max_llm_calls":0}
```

Статусы: `queued`, `preparing`, `running`, `completed`, `failed`, `cancelled`, `interrupted`. `preparing` означает фоновую дозагрузку пропусков выбранного биржевого источника, включая прогрев. Поле `progress` содержит текущий диапазон; `data_loads` — массив `{symbol,from,to,candles}` с выполненными загрузками. `cancel` работает и во время подготовки. Отдельный флаг для дозагрузки не нужен; DEMO/CSV остаются локальными и требуют ручного импорта недостающей истории. Если биржа не отдала полный диапазон, статус `failed`; подстановка свечей другого источника запрещена.

`backtest_progress` содержит `processed_candles`, `total_candles`, `current_symbol`, `last_candle_time` (время закрытия последней обработанной свечи текущей пары). Прогресс суммирует свечи всех пар на `[from,to)`, без прогрева; счётчик увеличивается только после полного решения. Ожидание очереди и загрузка истории — отдельные этапы, не проценты расчёта. Поля доступны также через MCP `get_backtest` / `list_backtests`.

При включённой LLM поле `llm_stats` содержит `responses`, `cache_hits`, `skipped`, `total_response_ms`, `average_response_ms`. Среднее — время от отправки HTTP-запроса до получения полного ответа для успешных обращений к модели в этом запуске, по всем парам. Кэш, ошибки и отменённые запросы исключены. `Decision.llm.response_ms` хранит длительность конкретного ответа; у кэшированных решений поле отсутствует. Если `responses=0`, среднее ещё не измерено (интерфейс показывает «—», не 0 мс). Старые отчёты без замеров также показывают «—». Текущие счётчики живут в памяти; при завершении, штатной отмене или ошибке сохраняются с отчётом. При аварийном завершении процесса текущие замеры могут быть потеряны.

Одинаковая двухэтапная проверка LLM используется в бэктестах и paper/live-сессиях. Сначала вычисляются условия без LLM; `all` прекращается на первом ложном/неготовом условии, `any` — на первом истинном. Неопределённая LLM-ветка откладывается, пока остальные ветки не проверены. Если итог активных правил зависит от модели, выполняется один вызов на свечу/пару и правила перепроверяются с четырьмя полученными оценками. Неактивные по позиции правила не вызывают модель; входы, на которые ссылается активный выход, проверяются лениво с виртуальным `position=none`. При возможном конфликте входов обе стороны должны быть разрешены до открытия позиции.

`Decision.llm_status`: `skipped` (ответ не требовался), `evaluated` (получен ответ), `cached` (взят из кэша), `not_ready` (недостаточно свечей для LLM). `llm_stats.skipped` суммирует `skipped` по всем парам, не расходуя бюджет запросов. `Decision.llm` отсутствует при пропуске. `Trace.skipped` и `reason` объясняют короткое замыкание/неактивную позицию, `needs_llm` — отложенную зависимость; окончательная необходимость определяется верхним узлом, а не отдельным дочерним условием. Дети trace остаются в порядке исходной стратегии, даже если вычислялись в другом порядке.

Пересечения полей `llm.*` требуют замеров на соседних свечах. Если предыдущий ответ пропущен, текущее достигнутое условие может вызвать модель, но пересечение остаётся неготовым; подстановка старого значения и ретроспективные вызовы не выполняются. В сессиях оценка от более ранней, несоседней свечи также не используется как предыдущее значение.

Доступные свечи фиксируются при создании задания; полный `input_data` сохраняется после дозагрузки, до первого расчёта/вызова LLM. После каждой полностью обработанной свечи доступны согласованные `candles`, `decisions`, `equity`, `fills`, `trades` и метрики пары. В момент ожидания LLM виден предыдущий готовый результат, без незавершённой свечи. При `failed`/`cancelled` рассчитанный префикс текущей пары сохраняется вместе с завершёнными парами, без принудительного закрытия позиции. Общие метрики вычисляются только при полном завершении. `interrupted` ставится незавершённым заданиям, включая `preparing`, при перезапуске; аварийное завершение процесса может потерять промежуточные данные в памяти.

Для `failed` доступна кнопка **Продолжить**, REST `POST /api/runs/{id}/resume` с `{}` и MCP `resume_backtest` с `{ "id": "…" }`. Продолжение сохраняет ID, `created_at`, снимок версии стратегии, входные свечи, расходы, пары, даты и общий лимит LLM. Параметры формы и новые версии стратегии не используются; поля для изменения конфигурации в запросе запрещены. Готовые свечи/пары не переоцениваются, восстанавливаются баланс, открытая позиция, ожидающее исполнение и предыдущие значения индикаторов/LLM. Свеча, на которой произошла ошибка, вычисляется заново целиком. Прогресс и статистика ответов продолжают накапливаться. Одновременные запросы не создают второй worker. `resume_count`, `last_resumed_at`, `failures` сохраняют историю продолжений и ошибок. Если сбой случился при загрузке истории, продолжается подготовка недостающих данных.

`llm_requests` учитывает отправленные запросы, включая неудачные. Продолжение не обнуляет `max_llm_calls`; при исчерпанном бюджете новый вызов останется запрещён. Подключение модели (адрес, ключ, таймаут, режим JSON) фиксируется отдельно в приватном `settings/run-llm-{id}.json` при создании запуска и не попадает в экспорт Run. Старые отчёты не содержали этого снимка: при первом продолжении используется текущее подключение с явной пометкой `resume_note`. Старый запуск без согласованного сохранённого состояния не возобновляется с выдуманной позиции: API возвращает ошибку. Продолжение поддержано только для `failed`, включая после штатного перезапуска сервиса; `cancelled`, `interrupted` и `completed` не возобновляются.

Поля `PairResult`: `complete`, `open_position`, `pending_action`, `balance`, `unrealized_pnl`. Метрики пары включают текущую оценку открытой позиции и уже уплаченные комиссии; `trades`/win rate учитывают только закрытые сделки. Интерфейс до конца запуска показывает метрики выбранной пары с явной пометкой, поскольку пары вычисляются последовательно. Итоговые метрики запуска относятся ко всему портфелю.

Для `/updates` параметр `after` — URL-кодированный JSON, например `{"BTCUSDT":{"candles":120,"fills":8,"trades":3}}`. Без `after` возвращается весь рассчитанный префикс, без `input_data`. Ответ: `{run,pairs:[{from,next,reset?,pair}]}`. `run` содержит метаданные и прогресс; в `pair` массивы содержат только новые элементы, а метрики и открытая позиция — текущий полный снимок. `candles`, `decisions`, `equity` используют один курсор `candles`; `fills` и `trades` — независимые. Добавьте новые строки к локальным массивам и используйте `next` в следующем запросе. При `reset=true` замените локальные массивы этой пары. Отрицательные курсоры/неизвестные поля отклоняются; курсор за пределами результата приводит к сбросу. Неизменившийся результат возвращает пустые массивы и актуальные метаданные.

Веб-интерфейс запрашивает обновления примерно раз в 1,2 секунды. «Следить за расчётом» выбирает текущую пару, конец графика и последнюю страницу решений; ручной выбор пары, прокрутка графика или страницы решений отключают слежение. Открытое дерево условий остаётся на выбранном решении. Промежуточный JSON можно выгрузить до конца прогона. MCP `get_backtest`/`get_decisions` также видят текущую рассчитанную часть.

## Позиция и ссылки на входы

Новые узлы Rule: `{"position":"none"}`, `{"position":"long"}`, `{"position":"short"}`. Как и сравнения, они вкладываются в `all`, `any`, `not`. Пример выхода из long по сигналу short:

```json
{"all":[{"position":"long"},{"signal":"enter_short"}]}
```

`signal` разрешён только внутри `exit_long`/`exit_short`, ссылается на существующее правило входа и проверяет его с виртуальным `position=none`; остальные значения индикаторов/LLM не меняются. Ссылки на выходы и ссылки внутри входов отклоняются, исключая циклы. Движок возвращает только один выход, без одновременного открытия противоположной позиции. `Decision.position` содержит фактическое состояние перед решением, trace раскрывает проверенное входное правило. Старые версии стратегий без новых узлов сохраняют поведение.

## Сессия

```json
{"strategy_id":"trend-demo","version":1,"exchange":"binance_futures","mode":"paper","symbols":["BTCUSDT"],"interval":"1h","capital":1000,"fee_bps":4,"slippage_bps":2,"max_order_notional":100,"allow_llm":false,"max_llm_calls":0}
```

`capital` — учётный бюджет, а не запрос изменения баланса биржи. В live комиссия оценочная, slippage не подменяет фактическую цену. `mode` и версия неизменяемы: создайте другую сессию. Максимум 10 работающих сессий. Статусы: `running`, `paused`, `stopped`.

Все режимы поддерживают `Strategy.setups`, абсолютные stop/target, `risk_fraction`, `max_notional`, `max_stop_fraction`, `max_entries_per_day`. План сохраняется в `Decision.plan`; live-intent `Session.pending` содержит `plan`, `balance_before`, `signal_time` и нормализованный `order`. Риск повторно проверяется после округления количества и получения свежей котировки. `slippage_bps` резервируется при sizing и оценке риска стопа, но подтверждённая цена live-исполнения не изменяется.

`Session.setups` хранит состояния событий по паре, `daily_entries` — `{day,count}` по дате исполненного входа UTC, `positions` — фактический объём с фиксированными уровнями и `initial_risk`. Повторная сверка не расходует квоту ещё раз. `SessionEvent.execution` и `Decision.execution` показывают план, рассчитанный риск, фактические параметры и причины пропуска; `SessionEvent.trade` содержит закрытую сделку с `pnl_r`, `fees` и `event_id`. Статусы аудита: `pending`, `filled`, `skipped`, `risk_breached`. При `risk_breached` реальная позиция сначала сохраняется, затем отправляется закрытие `reduceOnly`; незакрытое нарушение остаётся в `entry_violations`.

`reconcile` проверяет pending по client ID. Терминальный ответ (`FILLED`, `CANCELED`, `EXPIRED`, `REJECTED`, `EXPIRED_IN_MATCH`) обрабатывается по подтверждённому исполнению. Отменённый/истёкший/отклонённый ордер с нулевым объёмом снимает pending без открытия позиции; для выхода это ошибка, сохраняющая позицию. Частичный терминальный вход получает защиту на фактический объём; `FILLED` требует полного объёма. `NEW`/`PARTIALLY_FILLED`, неизвестный ответ или терминальный частичный выход сохраняют pending и блокируют продолжение до сверки. После подтверждения рискованного входа `reconcile` также пытается закрыть его. Команда оставляет сессию на паузе.

В начале каждого прохода сессия фиксирует последнюю границу торгового интервала UTC, до запросов котировок и истории. Источник должен вернуть ровно запрошенный закрытый диапазон. Формирующиеся, будущие, лишние и пропущенные свечи отклоняются до расчёта и отправки ордера. H4/D1 становятся доступны только на закрытии соответствующего агрегата. Сигналы используют закрытые свечи, не текущую котировку.

`Session.input_data` хранит принятый исходный ряд с прогревом; следующие проходы дополняют его без изменения начала и уже принятых баров. Это сохраняет состояние EMA/ATR и совпадение с бэктестом на одинаковом исходном ряде, в том числе после сохранения/возобновления. Поле отсутствует в списке сессий и доступно в полной сессии. Максимум — 250 000 сохранённых свечей на пару, после достижения лимита сессия останавливается с ошибкой без сдвига начала истории.

Возобновление сохраняет ожидающие setups, уровни и runtime-историю смещений. Пропущенные свечи проверяют отмену/истечение ожидания; новые доступные события на них помечаются `missed`, без ретроспективного исполнения и LLM-запросов. Участвующий setup расходуется при создании валидного плана даже при последующем пропуске отправки; дневной счётчик увеличивается только по подтверждённому входу. Локальные stop/target проверяются работающей сессией каждые 5 секунд и не действуют во время паузы или остановки сервиса.

Ордера правил разрешены только в техническом окне `[Decision.time, Decision.time + 5s)`. На 30-й секунде вход не допускается, повторный внутрисвечной проход не переоценивает сигнал. Задержка данных, LLM, котировки, подготовки ордера или записи intent приводит к `hold` с причиной `candle execution window missed; waiting for the next boundary`. Передача ордера ограничена оставшимся временем окна; при неизвестном результате отправки сохраняется pending для reconciliation. Пропущенное окно не переносит старый сигнал на следующую свечу. Защитные и ручные выходы продолжают работать вне этого окна. Совпадение рыночной цены live-исполнения с историческим open не гарантируется.


## Пример CLI

```sh
curl --fail-with-body http://127.0.0.1:8080/api/runs \
  -H 'Content-Type: application/json' \
  --data-binary @examples/backtest.json
```

При включённой авторизации добавьте `-H "Authorization: Bearer $ARCAM_API_TOKEN"`. Для повторяемого сравнения фиксируйте версию, даты, источник, пары, расходы и модель. Экспорт полного Run включает и входные данные, и все решения.

## LiquidAI/d1-2B

Для стратегии с нативными решениями d1 укажите:

```json
{"provider":"ollama","protocol":"systemone","model":"d1:2b","lookback":30,"instructions":"Evaluate trend and reversal risk from supplied closed candles and indicators."}
```

Это содержимое `Strategy.llm`. Полная стратегия: `examples/ema-d1-2b.json`; пресет и список протоколов доступны в `/api/catalog` как `d1_example` и `llm_protocols`. Поле `protocol` входит в неизменяемую версию. Пустой `protocol` означает `chat`. Для System One с provider=openai базовый URL включает `/v1`, endpoint — `/systemone`. Для provider=ollama endpoint — `/v1/systemone`.

Оценки `answers.<action>.noul` должны быть числами [0,1] для всех четырёх действий. Отсутствующее/неверное значение останавливает прогон. Журнал содержит сводку оценок, не текстовое объяснение модели. Кэш и бюджет вызовов общие с chat-индикатором.

## Расширения DSL

Контракт `Strategy` для контекстных индикаторов, выражений, setups и планов риска: [dsl-levels.md](dsl-levels.md). `get_catalog` / `GET /api/catalog` возвращают `dsl` с описанием и примером; валидация дополнительно возвращает `warmup_by_interval` в торговых барах. `get_backtest` включает `pending_plan`, `setups`, `entry_day`, `entries_today`; подробный аудит находится в решениях и сделках.
